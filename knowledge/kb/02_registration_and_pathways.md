# Registration & Pathways

## Before registering — confirm the Product bar
All three must be true: value to another user group · active lifecycle · ownership (PM, TL, Sponsor). Otherwise → Project Workspace.
- Registration works retrospectively (components already built is fine).
- MPP registers the product, not the deployment model — an offline tool can still be registered.

## Information to have ready
- Product name and description
- Charge Code — active, belongs to your org, aligned with pathway
- PM, TL, Sponsor — internal McKinsey employees only
- Data classification (Data Classification Model)
- Tech Class (KO103260)
- Practice Asset (if Practice Product) / Source Product (if Deployed Product)
- Asset inventory (warehouse, roles, service accounts, databases, cloud resources)

## Steps
1. Go to My Product Portal (My tab)
2. Start a new product registration
3. Complete all fields and review every tab
4. Submit — Product ID is generated at registration, not at approval
5. Associate existing technical components under Asset Inventory / Product Dependencies

## What to expect
- Accountable Leader auto-assigned (cannot be picked).
- Approval chain is sequential: AL approval → Launch Alignment. AL approval is the most common bottleneck; registrations have sat 6+ weeks when AL didn't act.
- No documented SLA — don't promise timelines. Launch Alignment estimates → launch@mckinsey.com.
- PSR required before production release. Working through the PSR Readiness Guide first brings review to under 1 week → #psr_support.

## Stalled approval
1. My Product Portal → My Requests
2. Open the request, check the approval workflow — who it sits with
3. Contact that approver directly. MPP cannot approve or bypass; approvers cannot be changed once submitted.

## Correcting a submitted registration
No "move back to draft". Options:
- Small fixes: let approval complete, then edit as normal self-service (most fields editable post-approval by PM/TL). Preferred.
- Fundamental change: My Requests → Cancel the Request → new registration → Submit (restarts approval clock).
- Ask in #my-product-portal whether a field can be amended in-flight.

## Pathways
- **Practice Product** — built by cell/cell tech group, client service delivery, commercially viable (asset fee/chargeback), linked to proprietary asset. Practice Asset mandatory: existing asset from dropdown, not free text. Don't create a duplicate Practice Asset to clear the field — it misroutes AL approval. Notify Practice Product/DPL contact for DPL list updates.
- **CCN Tool** — small-scope internal tool, not commercially viable, aids small aspect of internal process.
- **Deployed Product** — client-specific instances maintained by separate delivery teams; Source Product mandatory.
- **Other Product** — built/used by an administrative Firm function to manage its own processes. Self-service.
- **CTE Product** — built and maintained by Core Tech Ecosystem members. Self-service.
- Pathway changes to/from Practice Product or CCN Tool → MPP Team (Finance model impact).

## Single vs multiple Product IDs
See Decision Engine §9. Two plugins/modules don't automatically mean two products. Different data classifications → separate IDs is the safer route. Governance view → tech_risk@mckinsey.com.

## Scope change / new version
No re-registration. Update existing record (description, tech class, capabilities), refresh the IRP for the new scope/risk profile, submit for re-approval if required. Versioning not enabled in MPP.
